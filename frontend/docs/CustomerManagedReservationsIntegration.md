## C. Confirmed API integration

Base URL and Bearer injection remain in the existing Axios client. Only Customer actions were added; management approve/reject/activate/capacity writes remain blocked by the new endpoint rules.

| Method | Endpoint | Use |
|---|---|---|
| GET | `/public/facilities` | Paginated eligible Facility options; endpoint itself limits results to active Facilities |
| GET | `/pricing-rules` | Paginated active Managed PER_M3 terms, filtered by effective UTC start date |
| GET | `/customers/me/profile` | VERIFIED gate for creation |
| GET | `/reservations/managed/capacity/:facilityId` | Interval availability |
| POST | `/reservations/managed/quote` | Authoritative rent/deposit quote |
| POST | `/reservations/managed` | Create reservation; map `data.reservation` and `data.quote` |
| GET | `/reservations/me` | Owned combined list/service discovery |
| GET | `/reservations/managed/:id` | Fresh owner-scoped Managed lifecycle/hold |
| PATCH | `/reservations/managed/:id/cancel` | Cancel unpaid RESERVED/CONTRACTED, including expired unpaid holds as permitted by Backend |
| GET | `/contracts/me` | Owned contracts |
| GET | `/contracts/:id` | Verified contract detail/context |
| PATCH | `/contracts/:id/sign` | Owner signature, no body |
| POST | `/reservations/managed/:id/mock-pay` | Explicitly enabled development simulation only |

Quote/create payload is restricted to `facilityId`, `allocatedCapacityM3`, `startDate` and `term:{value,unit}`. Positive finite m³, safe positive integer term with DAY/MONTH/YEAR, ObjectId and valid future ISO UTC are validated. No owner, storageUnit, money, status or snapshot is sent. Backend remains authoritative and rechecks capacity transactionally. Calendar end-date display reuses the existing UTC calendar helper; server-returned quote dates are checked against the requested interval.

## D. Service routing

Self Storage keeps `/reservations/:id/cancel`, `/reservations/:id/mock-pay` and ACTIVE simulated unit access. Managed uses only `/reservations/managed/:id/cancel` and the gated Managed mock-pay. Existing Customer detail avoids generic Backend Self Storage ID reads and uses the owner collection first. Managed-specific detail is then fetched and its ID/service checked. Mutations re-read context before sending, validate the returned ID/status and refresh only after confirmation.

## E. Managed booking

Facility → future UTC date → actual effective PER_M3 term → positive quota → capacity check → Backend quote → explicit confirmation → create → existing reservation detail URL.

Input changes invalidate capacity, quote and confirmation. Busy refs prevent concurrent double-click requests; authenticated session/input guards prevent stale async results. Unverified Customers can view quotes but cannot create. Insufficient quota/configuration errors do not produce a success state. A quote is advisory and does not guarantee availability.

A create failure with a definitive 4xx invalidates the quote and requires another check/review. Network, 5xx or malformed success responses are ambiguous: creation remains disabled in that mounted form and the user is directed to My Storage. No mutation is automatically retried. Backend does not provide a create idempotency key; users must verify existing bookings before intentionally starting another booking after an ambiguous result.

## F. Contracts and payments

Self Storage money retains `pricingSnapshot.estimatedRent/depositAmount`. Managed reads only `pricingSnapshot.amountBreakdown`; currency comes from `pricingSnapshot.pricingRule.currency`. Missing money is omitted, never defaulted or inferred. Quote does not return totalDue, so no authoritative total is calculated by FE. Managed contract snapshots do provide totalDue and it is displayed when returned.

Contract context combines owned contract detail and fresh reservation data because contract DTOs do not expose the complete hold/quota context. Managed DRAFT signing requires CONTRACTED and `expiresAt > now`. A timer removes signing/payment actions when the hold expires; Backend status remains unchanged. Signing refreshes both contract and reservation context.

Managed mock-payment UI and dispatch require `import.meta.env.DEV === true` and `VITE_MI_MOCK_PAYMENT_ENABLED=true`. Default development and all production builds disable it. Backend separately requires non-production `NODE_ENV`, `MI_MOCK_PAYMENT_ENABLED=true`, a signed contract and a valid held CONTRACTED reservation. The FE cannot discover that server flag in advance: a disabled Backend response is shown safely, without local success. Self Storage simulation behavior is preserved. No provider, receipt, refund or financial record is fabricated.

- MI-02A eligibility date validation discrepancy, physical inbound/outbound and measured stock utilization are not implemented or changed by this task.
- Production deployment still requires configured quota/hold, exact PER_M3 pricing, deposit policy and MongoDB transaction support.

# Managed Inventory image uploads — Phase 1 (IMAGE-01 to IMAGE-03)

## Scope and access policy

This flow uploads Customer Managed Inventory Item photos through the authenticated Backend. It is separate from Avatar uploads, Staff inspection evidence, and signed Contract proof uploads.

Phase 1 uses Cloudinary `upload` delivery URLs, which are publicly retrievable by anyone who has the URL. These URLs are suitable only for non-sensitive development Item photos. The Backend rejects new image uploads when `NODE_ENV=production` until a private delivery policy and compatible signed image delivery are implemented. Public URLs are not private storage. Existing legacy HTTP(S) images continue to render as before.

Cloudinary credentials belong in the Backend environment only:

```env
CLOUDINARY_CLOUD_NAME=<development-cloud-name>
CLOUDINARY_API_KEY=<development-api-key>
CLOUDINARY_API_SECRET=<development-api-secret>
```

Never define `CLOUDINARY_API_SECRET` in a Vite environment or expose it to the browser. Cloudinary folder and public ID are generated by the Backend.

## API

`POST /api/v1/inventory-items/image-uploads`

- Authorization: authenticated `CUSTOMER`.
- Multipart form fields: `file` (one image), `managedReservationId`.
- Header: `Idempotency-Key` (8–128 allowed characters).
- Reservation must pass `requireManagedInventoryReservationForRegistration`: owned Managed Inventory reservation with active Managed Facility and positive allocated capacity; v2 status must be `DEPOSIT_PAID` before first registration or existing `ACTIVE`.
- Maximum: 8 MiB per file, 6000 pixels per side, 24 megapixels, one frame, JPEG/PNG/WebP, 20 outstanding uploads per Reservation, and 30 upload requests per IP per 15 minutes.
- The Backend decodes the bytes with Sharp, checks the decoded format against the multipart MIME, verifies dimensions, and hashes the original bytes. It uploads the original buffer without image recompression.
- Response: `{ success: true, data: { uploadId, secureUrl, publicId, width, height, format, expiresAt } }`.

`DELETE /api/v1/inventory-items/image-uploads/:uploadId`

- Authorization: upload owner only.
- Attached uploads cannot be deleted. Removing an unused upload from the form marks it for discard; Cloudinary deletion is deferred until its 24-hour expiry.

Inventory Item `POST`/`PATCH` keeps `images: string[]` of HTTP(S) URLs. Existing URLs already on that same Item remain valid for backward compatibility. Each newly added URL must exactly match an unexpired upload record owned by the current Customer and the Item's Managed Reservation. Item image URLs and upload state change in one MongoDB transaction. An upload can attach to one Item only.

## Quota, partial failure recovery, and cleanup

Before contacting Cloudinary, the Backend creates a durable `UPLOADING` record with a Backend-generated public ID and one of 20 unique quota slots per Customer/Reservation. A unique partial index arbitrates simultaneous slot claims; legacy unattached records without a slot are counted conservatively before assigning new slots. Attaching or fully deleting an upload releases its slot. Concurrent requests cannot rely on `countDocuments` alone for the cap.

The record is finalized as `UNATTACHED` only after Cloudinary returns validated metadata. A retry with the same idempotency key and same bytes reuses the same public ID and overwrites only that server-owned asset. If Cloudinary succeeded but MongoDB finalization failed, the durable `UPLOADING` record allows that retry to recover. If the Customer never retries, cleanup deletes the recorded public ID after the 24-hour retention window. If the initial record cannot be persisted, Cloudinary is never called.

Backend cleanup runs every 15 minutes. It transactionally checks for an Item reference and atomically claims expired `UPLOADING`/`UNATTACHED` records into `DELETE_PENDING`; attachment only accepts `UNATTACHED`, so an image claimed for deletion cannot subsequently attach. Attached Item images are never selected for automatic cleanup. Retry workers atomically claim `DELETE_PENDING` records using a 30-minute lease; an expired lease makes the operation recoverable after a worker crash. Cloudinary deletion failures remain retryable with exponential backoff capped at 24 hours, indefinitely.

Cloudinary deletion is idempotently retried if it succeeds but MongoDB cannot record `DELETED`: after the lease expires, another worker repeats the delete and then updates the record. A Cloudinary upload followed by failed metadata finalization is recoverable from the pre-existing `UPLOADING` record as described above. Provider calls and MongoDB writes cannot share a distributed transaction, so recovery depends on the durable metadata, stable public ID, leases, and Cloudinary's repeat-delete behavior.

MongoDB transaction guarantees require a replica set or sharded cluster. The automated tests use model/session mocks; deployment must have replica-set transaction support. No migration or data seed is required, but the new Mongoose model uses the `inventoryimageuploads` collection and creates its declared indexes. Verify the unique quota-slot index is ready before enabling uploads in a multi-instance development environment.

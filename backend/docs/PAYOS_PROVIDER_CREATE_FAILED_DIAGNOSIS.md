## SDK and request contract verified locally

The installed and lockfile-resolved package is `@payos/node@2.0.5` (not a floating newer version). The local `lib/resources/v2/payment-requests/payment-requests.d.ts` declares `paymentRequests.create(CreatePaymentLinkRequest, RequestOptions?)`, with numeric `orderCode` and `amount`, string `description`, `cancelUrl` and `returnUrl`, and optional `items`. Its success DTO includes `orderCode`, `amount`, `currency`, `paymentLinkId`, `status`, `checkoutUrl` and `qrCode`.

WDP currently calls the matching `sdk.paymentRequests.create(data)` API. SDK source marks the operation as `create-payment-link` and computes the request signature using the configured checksum key. The WDP mapping sends only the five required fields. The immutable intent supplies the order code and backend-calculated positive whole-VND amount; URLs are built from the validated server-side `PAYOS_CUSTOMER_ORIGIN`, and the description is generated by WDP and truncated to 25 characters. No client amount, provider identity or return URL is trusted.

The SDK `APIError` shape in the installed version has `name`, `status`, `headers`, `error`, `code` and `desc`. It uses subclasses including `BadRequestError`, `UnauthorizedError`, `ForbiddenError`, `NotFoundError`, `TooManyRequestError`, `ConnectionError`, `ConnectionTimeoutError`, `UserAbortError` and `InvalidSignatureError`. Provider descriptions and the error object may contain raw response details; WDP does not log them. A network error may have no HTTP status or PayOS code. Such fields must be reported as `UNKNOWN`, not inferred from the message.

The installed SDK defaults to a 60,000 ms request timeout and two retries. It retries connection failures, HTTP 408, 429 and 5xx responses. This is unsafe for a financial POST with an ambiguous outcome: PayOS may have created the link before the response was lost. WDP now sets `maxRetries: 0` specifically for `paymentRequests.create`; the original Payment is left `UNKNOWN` for order-code reconciliation. The PayOS client logger is explicitly set to `off`, so an inherited `PAYOS_LOG=debug` cannot cause SDK request diagnostics to print the POST body or response details. WDP emits only its own allowlisted warning record.

These local findings agree with the [official PayOS Node SDK README](https://github.com/payOSHQ/payos-lib-node/blob/main/README.md), the [official Node SDK guide](https://payos.vn/docs/sdks/back-end/node/) and the [PayOS payment request API reference](https://payos.vn/docs/api/). The SDK declarations and implementation installed in `node_modules` are the evidence for the exact version used by this workspace.

## Safe diagnostic record

At the `gateway.create()` failure boundary, WDP logs only:

- `correlationId`: the existing 16-character hash derived from the internal Payment ID.
- `stage` and a normalized error `category`.
- `sdkErrorName`: from a short allowlist; otherwise `UNKNOWN`.
- `providerHttpStatus`: a validated integer status or `UNKNOWN`.
- `providerErrorCode`: a short, allowlisted-shape code or `UNKNOWN`.
- `networkErrorCode`: only a known Node/Undici network code or `UNKNOWN`.
- Whether the create call was invoked, whether an HTTP/provider response was received, and whether checkout persistence/readback was confirmed.

Categories are `PAYOS_PROVIDER_AUTH_ERROR`, `PAYOS_PROVIDER_VALIDATION_ERROR`, `PAYOS_PROVIDER_RATE_LIMITED`, `PAYOS_PROVIDER_NETWORK_ERROR`, `PAYOS_PROVIDER_TIMEOUT`, `PAYOS_PROVIDER_SDK_ERROR` and `PAYOS_PROVIDER_UNKNOWN_ERROR`. HTTP 401/403, 400/422 and 429 are separated. A response-side SDK parse/signature error is marked as response received; a timeout/network failure without a response is not. A generic or malformed error remains unknown.

The logger never serializes the Error object and never records `message`, `stack`, `headers`, raw response/body, credentials, URL, QR, banking data, or Customer fields. Existing public failure behavior remains HTTP 503 `PAYOS_CHECKOUT_OUTCOME_UNKNOWN`; the diagnostic classification is internal only.

Other checkout stages keep their existing, non-provider classifications, such as claim unavailable, response identity mismatch, persistence failure, readback failure and original-order lookup failure.

## Request and failure analysis

The relevant path is `createCheckout()` → `createIntentTransaction()` → `createProviderLink()` → `gateway.create()` → response identity validation → write READY checkout fields → readback. The Payment intent and unique order code are created before the provider call. `createProviderLink()` claims the original intent as `CREATING`; a thrown provider/SDK error is persisted as `UNKNOWN` where possible and surfaced as the existing 503. A valid response is accepted only if order code, amount, VND currency, provider link ID and HTTPS checkout URL match validation. Link/QR values are written only onto the same immutable Payment intent and read back before success is returned.

The previous Render line `PROVIDER_CREATE_FAILED` is consistent with any exception thrown before `gateway.create()` resolves. It cannot distinguish provider validation/authentication, connection timeout, network failure, SDK parsing/signature failure or a lost response. The old correlation ID cannot be enriched retroactively from this code change. The current source contains no evidence that the Render endpoint/tunnel caused the failure.

Environment configuration is read server-side from `PAYOS_CLIENT_ID`, `PAYOS_API_KEY`, `PAYOS_CHECKSUM_KEY`, `PAYOS_ENABLED`, `PAYOS_CUSTOMER_ORIGIN` and `PAYOS_WEBHOOK_URL`. The three credential variables are trimmed and checked for presence; their values are not logged or reported. Customer and webhook origins are parsed and validated before creation; production requires HTTPS. This code audit cannot confirm that the Render dashboard has the correct secret values, matching PayOS channel, or correct deployed version.

**Configuration-dependent item to confirm with PayOS:** WDP emits a 25-character description. The current PayOS API reference says `description` is limited to 9 characters for channels whose bank is not linked through PayOS. The local code truncates to 25 but cannot determine the account/channel type. This is a plausible validation cause only if that restriction applies to the configured channel; it is not the confirmed cause. Verify the channel policy with PayOS or use sanitized HTTP 400 diagnostics before changing the request contract.

## Error codes and operator action

| Diagnostic category | What the evidence establishes | Safe action |
| --- | --- | --- |
| `PAYOS_PROVIDER_AUTH_ERROR` | SDK surfaced HTTP 401/403 | Verify the credential pair and channel assignment in the provider dashboard without copying values into logs. Rotate/update only through the approved secret-management process. |
| `PAYOS_PROVIDER_VALIDATION_ERROR` | SDK surfaced HTTP 400/422 | Review the validated WDP payload constraints and provider channel-specific field limits. Do not alter the amount or the immutable intent. |
| `PAYOS_PROVIDER_RATE_LIMITED` | SDK surfaced HTTP 429 | Do not recreate the intent. Check provider throttling and query the original order code later. |
| `PAYOS_PROVIDER_TIMEOUT` | SDK timeout or HTTP 408 evidence | Treat as unknown; read-only lookup by original order code. Do not resubmit create. |
| `PAYOS_PROVIDER_NETWORK_ERROR` | A known network/connection failure was surfaced | Treat as unknown; check Render egress/DNS/TLS telemetry and query the original order code. |
| `PAYOS_PROVIDER_SDK_ERROR` | A known SDK error class/parse/signature error was surfaced without a more specific HTTP/network classification | Check installed SDK version and safe status/code fields; preserve intent and reconcile. |
| `PAYOS_PROVIDER_UNKNOWN_ERROR` | No reliable safe classification exists | Do not infer a root cause from the exception message. Preserve intent and request operator/provider review. |

`UNKNOWN` fields mean the SDK did not expose a safe value. Do not enable SDK debug logs to obtain more detail; they may include the request payload. Do not return internal categories to the Customer.

5. Apply funds only through the existing signed webhook verification and transactional settlement rules. Where current Reservation economics/state no longer match, preserve verified funds and require manual reconciliation.
